# Vertical slice: the browser leader against the real server

The harness (examples/browser-spike) runs the real leader worker (`src/client`) against the landed
Postgres server (`src/server/postgres`) through a small Bun entry, examples/server/main.ts. Nothing in
`src/server` or `src/core` is specific to the slice.

```
┌──────────────┐  Effect RPC   ┌──────────────┐  HTTP POST + NDJSON  ┌──────────────┐   ┌──────────┐
│ tabs (main.ts│──────────────▶│ leader worker│─────────────────────▶│ Vite :5199   │──▶│ Bun :5200│──▶ PG17
│ window.echo) │  MessagePort  │ OPFS SQLite  │  /sync               │ proxy /sync, │   │ /sync,   │
└──────────────┘               └──────────────┘                      │ /admin       │   │ /admin   │
                                                                     └──────────────┘   └──────────┘
```

## The app

examples/browser-spike/app.ts is shared by both sides: one synced table, `todos`
(`id`, `accessScopeId`, `title`, nullable `note`), and four mutations.

- `t` writes nothing. The substrate scenarios use it.
- `todos.add` inserts a todo. The server's copy adds checks the client cannot evaluate. A title containing
  `server-rejects` fails with the declared domain error `{ reason: "blocked-title" }`, so the
  rejection reaches the client only as a ledger outcome. A title containing `[gate:NAME]` parks the server
  handler inside the push transaction, before any write, until `/admin/open?gate=NAME`. S2 and S5 use it to
  hold the server's answer for exactly as long as they assert.
- `todos.update` patches the fields it names (`title`, `note`) of an existing todo, with the same server-only
  `server-rejects` title check. `todos.delete` deletes one. On a missing row both fail with the store's
  `RowNotFound`, which the server records as a `Rejected` outcome.

## The server entry (dev only)

examples/server/main.ts:

1. Creates the database `ECHO_SLICE_DB` (default `echo_slice`) if it is missing.
2. Builds `Startup.layer` before listening. That runs the engine migrations, the app migration
   examples/server/migrations/001_create_todos.ts and 002_add_todo_note.ts (generated by core
   `Migrate.generate`), `attach`,
   and `Migrate.verify`. On `Drift` it prints every mismatch and exits 1 without listening.
3. Serves core `SyncRpcs` (HTTP POST with NDJSON) at `/sync`.

It is the worked example for docs/getting-started.md. A database created by an older version of this
entry (tables but no `echo_sync.app_migrations`) fails migration 001 with "relation already exists".
Drop it once: `DROP DATABASE echo_slice`.

**`principalFor` is app-owned (DESIGN §4). This entry's implementation is a dev shim:** it trusts the
`x-echo-principal` request header, which the harness leader sets to its tab's `?principal=`. There is no
authentication. Only examples/server reads the header; nothing in `src/server` does. A real app
authenticates the request (session cookie, bearer token) in its own `principalFor`.

The leader sends credentials with `LeaderOptions.syncHeaders(principal)`, an `Effect` of headers. It is
a `src/client` API: `Transport.layerProtocolHttp(url, headers)` runs that Effect for every HTTP request
(each push, pull and pokes (re)connect) and puts the result on it. Tests in `Transport.test.ts` check
all three, renewal without a leader restart, and one evaluation per request.

`/admin/*` exists only so the scenarios can drive and observe the server:

| Route | Does |
| --- | --- |
| `grant?scope=&principal=&role=` | creates the scope if needed and inserts the grant (default role `writer`) |
| `revoke?scope=&principal=` | deletes the grant |
| `ledger?mutationId=` | every `echo_sync.mutations` row for that id, across clients |
| `todos?scope=` | the server's `todos` rows in a scope |
| `open?gate=` | opens a scenario gate (see the app) |
| `rejections?enabled=0\|1` | turns the server's `server-rejects` title check off or on (the `no-reject` control) |
| `stats?clientId=&todo=` | RPC requests this process received per tag for a client; how often the server's `todos.add` handler started for a todo id |

The Vite harness proxies `/sync` and `/admin` to the server (`ECHO_SLICE_SERVER`, default
`http://127.0.0.1:5200`). When the server dies mid-response, Vite's proxy keeps the browser's pokes
response open indefinitely. Scenario 5 caught this before liveness existed: after a restart an idle client
sent no request for 121 s, and the harness carried a proxy workaround (destroy the browser response when the
upstream ended incomplete). That workaround is gone: the client's `idleTimeout` (DESIGN §6 Liveness, default
45 s; the server heartbeats every 15 s) ends a stream that delivers nothing, so scenario 5 now catches up
through the idle timeout and the reconnect backoff, as any client behind such a proxy would.

## Running it

```sh
# PostgreSQL on localhost:5432 (.agents/setup prepares one; or any server, e.g.
#   docker run -d --name echo-pg -p 5432:5432 -e POSTGRES_PASSWORD=echo postgres:18)
bun examples/server/main.ts &         # the slice server on :5200 (scenarios.sh needs it; slice.sh starts its own)
bun run spike &                       # Vite harness on :5199

examples/browser-spike/scenarios.sh   # the 18 substrate scenarios (real-server mode by default)
examples/browser-spike/slice.sh       # the 12 vertical-slice checks (always real server)
```

slice.sh runs four sections, in the order `SLICE_ORDER` lists them (default
`base offline conflict deleteedit`): `base` is S1–S5, the others are S6–S8. Each of S6–S8 uses its own
scope and its own two client profiles, so the sections are independent of order; run
`SLICE_ORDER="deleteedit conflict offline base"` to check that. `SLICE_CONTROL=<name>` injects one
deliberate fault or skipped step (table below) that must make its check fail; combine it with
`SLICE_ORDER=<section>` to run only that section.

**Network gate.** `echo.setOffline(true|false)` takes one identity (`app`/`profile`) offline: its leader
worker's requests to the sync URL reject with a `TypeError`, as `fetch` does when the server is
unreachable, and responses that are still streaming (the pokes stream) are aborted. Other requests, such as
the SQLite wasm, still load, as they would from cache on an offline device. The state is kept in
`localStorage`, and the page passes it to each leader worker it spawns, so a reload while offline starts a
leader that is still offline. A check treats the gate as in effect only once a sync attempt has failed with
`lastError.kind === "network"`, so a halted push can never pass for offline.

`ECHO_PG_URL` (default `postgres://postgres:echo@localhost:5432/postgres`), `ECHO_SLICE_DB` and
`ECHO_SLICE_PORT` (default 5200) configure the server. slice.sh starts `examples/server/main.ts` itself,
restarts it in scenario 5, and stops it on exit (`ECHO_SERVER_LOG` captures its output). To run against a
server you manage instead (for example a supervised service), start it before the run and set
`ECHO_SERVER_START` and `ECHO_SERVER_STOP` to the commands that start and stop it. Each run uses fresh app
ids, scopes and mutation ids, so runs never interfere and the database can be reused.

## Which server a scenario runs against

`open_tab` in examples/browser-spike/lib.sh decides, for every tab both scripts open:

- **Real server (default):** the tab's URL gets `syncUrl=<base>/sync`, so its leader syncs with the
  slice server.
- **Fake server:** a scenario whose URL already names a `syncUrl` keeps it. The two `sync:` scenarios
  point at `/fake-sync/rpc` (examples/browser-spike/fakeSync.ts), a fault injector whose push always
  answers `MalformedEnvelope`.
- **Local only:** with `ECHO_SYNC=off`, scenarios.sh adds no `syncUrl` (nothing syncs) and does not
  require the server. slice.sh always uses the real server.

Postgres ledger has exactly one row for each exactly-once mutation they enqueue (`before-handover`,
`retried-across-handover`, `crash-after-commit-1`, `survives-reload`).

### Controls (`SLICE_CONTROL`)

| Control | Fault | Fails |
| --- | --- | --- |
| `skip-offline` | A never goes offline, so its edit is pushed at once | S6 (ledger row while "offline", no network error) |
| `drop-outbox` | the queued entry is deleted from A's outbox before the reload | S6 (entry gone after the reload, edit never reaches Postgres or B) |
| `stay-offline` | A never comes back online | S6 |
| `b-offline-after-push` | B drops offline again once its own pushes are acknowledged, so it never pulls A's | S7a, S7b, S7c (B never sees the marker) |
| `a-first` | A reconnects before B | S7a (ledger order), S7b (B's title stands) |
| `no-reject` | the server's blocked-title check is switched off (`/admin/rejections?enabled=0`); A's input is unchanged | S7c |
| `transient-rejected` | B's replica shows A's rejected title for one emission and then B's again, so B's final state is correct | S7c (history scan) |
| `a-stays-offline` | A never comes back online | S8a, S8b |
| `skip-b-delete` | B does not delete the row A edits | S8b only (the row survives) |

Each control was run on its own section (`transient-rejected` and `no-reject` also in the full run); every
check not listed for a control still passed.

### What the slice does not prove

- S4's catch-up time is bounded by the pokes reconnect backoff (1 s doubling to 30 s), not by a resync
  timer: v1 has none (DESIGN §6). A client behind an intermediary that holds a dead response open, as
  Vite's proxy does, is deaf for up to `idleTimeout` (45 s) plus the reconnect backoff.
- S5 holds the first push open across the leader's closure, but when the gate opens the server may still
  commit that abandoned request, or roll it back and commit the successor's. Both outcomes must give one
  ledger row, so the check accepts either; the evidence line reports how many times the server's handler
  started (the deduplicated second push may skip the handler).
